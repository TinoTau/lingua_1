## Executive Verdict

# 当前分类器的**判断标准不完全符合**冻结架构

| 问题 | 结论 |
|------|------|
| 是否错误采用「不是专业术语 → Base」？ | **部分是。** 实现上大量代理成「无强标记词表命中 / 二字无标记 / pack 导入无标记 → Base」，等价于「看起来不够像术语 → Base」。 |
| 冻结标准应是什么？ | **「是否具有领域区分能力」**（能否帮助区分 utterance 细域），**不是**「是否专业/生僻/行话」。 |
| 7216→Base 是否可能误判？ | **是，存在系统性假阴性风险**；其中大量 meeting/tech 噪声迁回 Base 仍合理，但「会议 / 机场 / 开发 / 测试 / 预订」等被一并打入 A，标准过严。 |
| 是否需要 Runtime 三级：Base / Weak / Strong？ | **不建议作为 Runtime SSOT 三级。** Weak 若存在，应只是**运营人审工作流标签**，不得落成第二套库字段。 |
| 是否建议调整分类标准？ | **建议调整「分类标准与操作定义」**（仍保持 Base vs Domain 二元合同）；**不**建议开发新状态机。 |

本轮**不改数据、不开发**。

## 1. 当前分类器存在的问题

### 1.1 判据漂移：从「区分能力」滑向「标记表 / 术语感」

冻结判据：

```text
该词是否具有领域区分能力？
  有 → 允许 term_domain_tags（Domain）
  无 → tags 必须为空（Base）
```

分类器实际主路径（代码事实）：

```text
命中 DOMAIN_MARKERS 强标记表？
  是 → B/C（保留或纠错）
  否 → 若在 meeting/tech 或 pack 导入 → 多数直接 A（Base）
```

这在工程上近似：

```text
“像专业术语 / 命中白名单”
        ↓
      Domain
“不像 / 未命中”
        ↓
      Base
```

与冻结标准**不等价**。

**反例（有区分力但被当 Base）：**

| Term | 当前桶 | 为何有区分力 | 分类器为何判 A |
|------|--------|--------------|----------------|
| 会议 | A | 强指向 meeting / 会务场景 | 落入弱二字表 / 「无区分力」启发 |
| 机场 | A | 强指向交通/接送机语境 | 无标记 + 污染 → 直接 A |
| 开发 / 测试 | A | 偏 tech 场景信号（弱～中） | 二字无标记 → A |
| 预订 | A | 酒店/餐饮/出行场景信号 | 无标记 + 多域污染 → A |

**正例（无区分力、判 A 正确）：**

| Term | 当前桶 | 说明 |
|------|--------|------|
| 今天 / 大家 / 经理 / 客户 / 问题 / 安排 | A | 跨行业通用，符合 Base Only |
| 上帝 / 上午 / 一定 | A | meeting 灌入噪声，应 Base |

### 1.2 「强标记表」把 Domain 缩成「Strong Lexicon Term」

`DOMAIN_MARKERS` 本质是**高置信术语种子**（拿铁、房卡、登机牌、议程…）。  
用它做 **B 的充分条件**合理；用「未命中」做 **A 的充分条件**则过强——把「Weak-but-discriminative」和「Non-discriminative」混进同一桶。

### 1.3 长度启发式放大误判

`short_unmarked_in_meeting_or_tech`（A 中 **6336/7216**）几乎等于：

```text
二字 + 无标记 + 现挂 meeting/tech
        ↓
      一律 Base
```

二字词里既有噪声（上帝），也有场景锚点（会议、开发、测试、机场）。**长度不是区分能力。**

### 1.4 与冻结 Runtime 合同的另一处错位

冻结架构只承认：

```text
tags 空 = Base
tags 非空 = Domain（可参与 Vote）
```

分类器输出的 A/B/C/D 是**审计桶**，不是 Runtime 状态——这点本身可接受。  
危险在于：若直接把「A=7216」当作金标去清空 tags，会把部分**有区分力**的 Domain 误删，损害 Vote 可用证据。

### 1.5 未违规但需分清的部分

| 做法 | 评价 |
|------|------|
| 禁止 `is_base` / `general_tag` 等第二套字段 | 与冻结一致（分类器也未引入） |
| 显式 Base Only 表（今天/大家/经理…） | 符合「无区分力 → Base」 |
| C 桶纠错（医生→meeting） | 数据质量问题，标准方向正确 |
| D 边界桶 | 方向正确，但与 A 的切割标准仍偏「标记表」 |

## 2. 为什么「7216 迁回 Base」可能存在误判

### 2.1 数量结构

| A 的 reason | Count | 误判风险 |
|-------------|------:|----------|
| short_unmarked_in_meeting_or_tech | 6336 | **高** — 一刀切二字 |
| pack_imported_no_discriminative_marker | 714 | **中高** — 「无标记」≠「无区分力」 |
| no_domain_discriminative_power | 166 | **低** — 多与显式 Base Only 对齐 |

因此：**7216 不是「7216 个无区分力词」的金标计数**；它是「未通过强术语过滤器」的上界估计。

### 2.2 误判类型

| 类型 | 含义 | 例子 |
|------|------|------|
| **假阴性（有区分力 → 被标 A）** | 标准过严 | 会议、机场、开发、测试、预订（争议见 §3） |
| **真阳性（无区分力 → A）** | 标准正确 | 今天、大家、经理、客户、上帝 |
| **假阳性（无区分力 → 仍非 A）** | 在 D/B，不在 7216 内 | D 中部分泛化细域词 |

对「7216」而言，主要风险是 **假阴性偏多**，不是「Base 迁回不够」。

### 2.3 与 Inflation 真相的关系（避免矫枉过正）

Meeting/Tech_AI Inflation **确实存在**（Contract Audit + Classification Audit 一致）。  
正确叙事是：

```text
Inflation 噪声必须回 Base
        ≠
所有未进强术语表的词都必须回 Base
```

若用 7216 作为清洗配额，会在消灭 Inflation 的同时，误伤一批 **弱但有用的场景锚点词**。

### 2.4 操作含义（仍不开发）

在调整标准之前，**不宜**把 A 全量当作可执行删除清单。  
可执行的高置信删除应优先：显式 Base Only、明显噪声二字、错域污染附加 tag；对「会议/机场/开发…」类先做人审。

## 3. Weak Domain 是否应该存在？

### 3.1 先定义「Weak Domain」可能指什么

| 含义 | 是否需要 |
|------|----------|
| **W1 Runtime 第三态**（库内 `weak_domain=true` / 第二套状态） | **否** — 直接违反冻结「禁止第二套状态」 |
| **W2 运营人审档**（工作表：待确认是否保留 tags） | **可以** — 仅流程，不入库 |
| **W3 同一 Domain 内的证据强度**（weight / Vote 权重） | **可以** — 仍只有 tags；强弱用 weight 表达，不是新类别 |
| **W4「有一点场景倾向、但单独不足以定域」的词** | **语义上存在**；合同上仍是「有 tags 的 Domain」或「空 tags 的 Base」二选一 |

### 3.2 对示例词的标准判断（区分能力，非术语感）

| Term | 是否有领域区分能力？ | 建议合同归属 | 上轮分类器 | 说明 |
|------|----------------------|--------------|------------|------|
| 拿铁 / 房卡 | 强 | Domain（Strong 语义） | B | 符合 |
| 入住 / 退房 / 签到 / 包车 / 上线 | 中～强 | **Domain**（应有 tags） | B | 符合；说明「非生僻术语」也可 Domain |
| 机场 | 中 | **Domain 倾向**（交通/接送） | A（误判风险） | 口语高频但仍区分场景；污染 tag 应洗，不是整词回 Base |
| 预订 | 弱～中 | **争议：偏 Domain 或 Base** | A | 跨酒店/餐饮/票务；单独定域弱，但非「今天」级零区分力 |
| 路线 | 弱～中 | Domain 或人审 | D | 旅游/交通相关 |
| 会议 | 中～强 | **Domain** | A（误判） | 非「专业术语」，但会务区分力明确 |
| 开发 / 测试 | 弱～中 | **Domain 倾向（tech）** 或人审 | A（误判风险） | 非黑话，但偏技术语境 |
| 经理 / 客户 / 今天 / 大家 | 无 | **Base** | A | 符合 |

**关键推论：**

- 「入住 / 退房 / 上线」证明：冻结标准下 **Domain ≠ 专业术语**；日常词只要能区分场景，就应允许 tags。  
- 「会议 / 机场 / 开发 / 测试」被打入 A，暴露分类器用了错误代理判据。  
- 「预订」才是真正的 **Weak（语义）** 边界：有场景气味，但多域共享——合同上应用「最少 tags 或空 tags」人审，而不是「因为不够专业 → Base」。

### 3.3 Weak Domain「是否真正存在」——结论

| 层面 | 结论 |
|------|------|
| 语言/运营层面 | **存在**连续谱：零区分力 → 弱锚点 → 强锚点 |
| 冻结 Runtime / 数据模型 | **不存在第三类**；只能落在 Base（空）或 Domain（有 tags） |
| 是否应发明 Weak Domain 入库状态 | **否** |

## 4. Weak Domain 与 Strong Domain 的区别（若仅作语义/人审用语）

仅作**人话分级**（不入库）时：

| | Strong Domain（语义） | Weak Domain（语义） | Base |
|--|----------------------|--------------------|------|
| 区分能力 | 高：单独出现即可强烈提示细域 | 中/低：有倾向，常需与其它证据合取 | 无：各域同等可能 |
| 例子 | 拿铁、房卡、登机牌、挂号、MRI、议程 | 机场、预订、开发、测试、路线 | 今天、大家、经理、客户、问题 |
| `term_domain_tags` | **应有**（少而准） | **可有可无**（人审；有则 ≤ 合同上限，禁堆多域） | **必须空** |
| Vote 角色 | 主证据 | 辅证据（靠 weight / 多词合取） | 不参与 |
| 与「专业术语」 | 常是术语，**不必须** | 常是日常词，**仍可能有区分力** | 日常或跨域套话 |

**Strong / Weak 不是第三 SSOT**，只是运营描述「这个 Domain 词证据有多强」。  
库内表达方式应仍是：`term_domain_tags` ± `weight`，而不是新列。

## 5. 运营维护建议（标准与流程，非开发方案）

1. **唯一入库问题改为：**  
   「该词是否具有领域区分能力？」→ 是则写 tags；否则清空。  
   **禁止**问：「这是不是专业术语？」

2. **清洗优先级：**  
   - P0：无区分力噪声（今天/大家/上帝…）与错域（医生→meeting）  
   - P1：Inflation 灌入的无场景二字垃圾  
   - P2：人审弱锚点（机场/预订/开发/测试/会议…）——**默认倾向保留最少正确域，而不是默认删光**

3. **人审三问（建议印在工单）：**  
   - 若只听到这个词，会不会更偏向某个细域？  
   - 它是否在多个不相关行业同等常用？  
   - 若保留 tags，能否把域数压到真正相关的 1～少数（遵守 ≤5），而不是「全行业」？

4. **不要**新增 `weak_domain` / `domain_role` / `is_base` 字段。  
   人审档用表格列（CSV/工单）即可。

5. **权重：** 弱锚点可用较低 `weight` 表达「弱证据」；仍是 Domain，不是第三类。

6. **分类器输出：** A/B/C/D 仅作审计线索；**A 全量不可直接当删除脚本输入**。

## 6. 是否建议调整分类标准？

### 6.1 建议调整什么

**建议调整：分类标准的操作定义（审计/人审用），使其回到冻结架构。**

| 项目 | 现状（分类器 v1） | 建议标准（V2） |
|------|-------------------|----------------|
| 核心问题 | 是否像术语 / 是否命中标记表 | **是否具有领域区分能力** |
| Domain 准入 | 强标记 ≈ 必要 | 强标记 = 高置信充分条件；**非必要条件** |
| Base 准入 | 无标记常直接 Base | 仅当「跨域同等常用 / 零场景偏向」 |
| 弱锚点 | 常进 A | 进 **人审（语义 Weak）**；默认更偏向保留正确单域 tags |
| Runtime 模型 | （未改）二元 | **保持二元** Base/Domain |
| 第二套状态 | 无 | **继续禁止** |

### 6.2 不建议做什么

- 不建议把 Weak Domain 做成库内第三类或 Runtime 分支。  
- 不建议本轮改代码 / 改 tags / 开发新分类器产品化。  
- 不建议用「7216」作为清洗 KPI。

### 6.3 与冻结架构的符合性总表

| 冻结原则 | 分类器 v1 | V2 标准建议后 |
|----------|-----------|----------------|
| Base = 无区分力、空 tags | 部分符合，假阴性过多 | 对齐 |
| Domain = 有区分力、可有 tags | 缩成 Strong Term | 恢复 |
| 唯一 SSOT = term_domain_tags | 符合 | 保持 |
| 禁止第二套状态 | 符合 | 保持；Weak 仅人审用语 |

## 必须回答（收口）

1. **当前分类器问题？** → 用「强标记/术语感/二字无标记」代理「领域区分能力」，导致标准漂移。  
2. **7216 为何可能误判？** → 其中 ~88% 来自二字无标记一刀切；会把会议/机场/开发等有区分力词打进 Base。  
3. **Weak Domain 是否应存在？** → 语义连续谱上存在；**Runtime/库内第三类不应存在**。  
4. **Weak vs Strong？** → 证据强度差异；入库仍是有无 tags；强弱用 weight/人审，不靠新字段。  
5. **运营建议？** → 改问法、分优先级清洗、弱锚点人审默认保留最少正确域、禁用第二套状态。  
6. **是否调整分类标准？** → **是（标准与人审定义）**；**否（Runtime 三级架构 / 本轮开发）**。
